# Issue 2 Safe Diamond Parsing

## Summary

Replace dynamic Python execution of diamond records with literal-only parsing so downloaded or edited data cannot run code when `csv.py` processes `diamonds.txt`.

## Problem Frame

Issue #2 was filed from the public repository security review because `csv.py` calls `eval(lines[i])` for every input record. The script processes data produced from a network scraping workflow, so malformed or attacker-controlled records could execute arbitrary Python on the operator's machine.

## Requirements

- R1. `csv.py` must not call `eval` or `exec` for diamond records.
- R2. Diamond records must still parse Python-literal dictionary lines generated by the legacy downloader.
- R3. Malformed records and non-dictionary literals must fail closed with a clear error.
- R4. The change must stay Python 2-compatible and avoid unrelated data-model or output-format changes.
- R5. The PR must reference `https://github.com/garethpaul/diamond-cost-predictor/issues/2` and be marked `URGENT`.

## Implementation Unit

### U1. Literal-Only Parser

- **Goal:** Introduce a small parser helper around `ast.literal_eval`, validate that each record is a dictionary, and keep the existing normalization and CSV output flow intact.
- **Files:** `csv.py`, `scripts/check-safe-parsing.sh`
- **Test Scenarios:** Verify no `eval(lines[i])` remains, literal parsing is used, non-dictionary records are rejected by source guard, and the script remains Python 2 source-compatible.
- **Verification:** `scripts/check-safe-parsing.sh`, `python3 -m py_compile csv.py`, and `git diff --check`.

## Risks

- This workspace does not provide Python 2, so full runtime verification of the legacy script is unavailable locally.
- `python3 -m py_compile` is a source-syntax check only; it does not execute the Python 2-style print statements in runtime mode.
